# DPF API タイムアウト最適化ガイド

## 問題の背景

Supabase Edge Functionsには**デフォルト60秒のタイムアウト制限**があります。
DPF APIからのデータ同期処理がこの制限を超えると、`AbortError`が発生します。

## 実装した最適化

### 1. 認証パターンの削減（最重要）
- **変更前**: 5つの認証パターンを順次試行（最大300秒）
- **変更後**: 2つの主要パターンのみ試行（最大40秒）
  - `X-Dpf-Api-Key`（標準・優先）
  - `Authorization Bearer`（次点）

### 2. 個別タイムアウトの短縮
- **変更前**: 各パターン60秒のタイムアウト
- **変更後**: 各パターン20秒のタイムアウト
- これにより、2パターン試行しても40秒以内に収まります

### 3. データベース操作のバッチ化
- **既存データ削除**: `mdel()`によるバッチ削除
- **新規データ保存**: `mset()`によるバッチ保存
- 1件ずつの操作と比べて、大幅に処理時間を短縮

### 4. 詳細なタイミングログ
各処理ステップで経過時間を記録：
```
Step 1: DPF APIデータ取得 (elapsed: XXXXms / 60000ms)
Step 2: データグループ化 (elapsed: XXXXms / 60000ms)
Step 3: データベース更新 (elapsed: XXXXms / 60000ms)
```

## 処理時間の目安

| 処理ステップ | 想定時間 | 説明 |
|------------|---------|------|
| DPF APIデータ取得 | 5〜20秒 | 認証パターン1つで成功した場合 |
| データグループ化 | 1〜3秒 | メモリ内処理 |
| データベース更新 | 3〜10秒 | バッチ処理により高速化 |
| **合計** | **10〜40秒** | 60秒制限内に収まる |

## トラブルシューティング

### タイムアウトが発生する場合

#### 1. Supabaseログの確認
1. Supabaseダッシュボードにアクセス
2. `Functions` → `make-server-5f24a873` → `Logs`を確認
3. 以下の情報を確認：
   - どのステップで時間がかかっているか
   - 認証パターンの成功/失敗状況
   - 合計経過時間

#### 2. ブラウザコンソールの確認
フロントエンド側でも詳細なログを出力：
```
=== DPF Sync Started ===
Start time: [timestamp]
Sending sync request to server...
Server response received after XXs
✅ Sync completed successfully in XXs
```

### よくある原因と対処法

#### ケース1: DPF APIが遅い（20秒以上）
**原因**: DPF APIのサーバーが混雑している
**対処法**: 
- 時間を置いて再試行
- DPF APIの管理画面で障害情報を確認

#### ケース2: 認証エラーで複数パターン試行
**原因**: APIキーが正しくないため、2つのパターンを試行
**対処法**:
- APIキーが正しいか確認
- DPF管理画面でAPIキーの権限を確認

#### ケース3: データベース更新が遅い
**原因**: 既存データが非常に多い
**対処法**: 
- 不要な古いデータを手動削除
- データベースのインデックスを確認

## 現在の設定

### サーバー側（dpf_graphql.tsx）
```typescript
// 認証パターン: 2つに制限
const authPatterns = [
  { name: 'X-Dpf-Api-Key（標準）', headers: { 'X-Dpf-Api-Key': apiKey } },
  { name: 'Authorization Bearer', headers: { 'Authorization': `Bearer ${apiKey}` } },
];

// 各パターンのタイムアウト: 20秒
setTimeout(() => controller.abort(), 20000);
```

### フロントエンド側（DpfSyncAdmin.tsx）
```typescript
// フロントエンドのタイムアウト: 120秒
setTimeout(() => controller.abort(), 120000);
```

## さらなる最適化が必要な場合

### オプション1: 非同期処理化
処理を完全に非同期化し、完了をポーリング：
1. フロントエンド → サーバー: ジョブ開始リクエスト
2. サーバー: ジョブIDを返して即座にレスポンス
3. バックグラウンドで処理を継続
4. フロントエンド: ジョブIDで完了状況を定期的にチェック

### オプション2: Supabase Functionのタイムアウト延長
Supabaseの設定でFunctionのタイムアウトを延長（Pro/Teamプラン）

### オプション3: データ量の削減
- `size: 1000` → `size: 500`に変更
- 複数回に分けてデータを取得

## まとめ

現在の最適化により、通常は**10〜40秒**で処理が完了し、60秒制限内に収まるはずです。
それでもタイムアウトが発生する場合は、上記のトラブルシューティング手順に従ってください。
